# Dinedot — project notes

QR table ordering for restaurants: guests scan a table QR, order from the menu, see live status, get the guest Wi-Fi, call a waiter, split the bill, tip and pay by UPI, then rate the visit. Staff run it from one app: kitchen screen, floor map, bills, menu, tables & QR, dashboard, settings. "Dinedot" is a working name. This repo is the **template**: each restaurant gets its own copy on its own Supabase project (same pattern as Studio CRM).

## Stack (same family as Vroombrite)
- Plain static HTML/CSS/JS, no build step, served by GitHub Pages from the root of `main`. No framework.
- **Supabase** (Mumbai region) for data. Schema, security and every function are in `supabase/migrations/` (run in order). `supabase/sample_menu.sql` is optional sample data. Tests: `supabase/test/run.sh` (needs a local Postgres; set PGHOST/PGPORT/PGUSER) runs `test.sql`, `test_0003.sql`, `test_0004.sql` (two restaurants kept apart), `test_0005.sql` (discounts, takeaway, split payments, stations, day close, notice) and a real two-connection race test on fresh databases → `ALL TESTS PASSED`, `0003 TESTS PASSED`, `0004 TESTS PASSED`, `0005 TESTS PASSED`, `RACE TEST PASSED`. Browser journey: `python3 -m http.server 8765 &` then `node tests/e2e/flow.mjs` → `E2E PASSED`. GitHub Actions (`.github/workflows/test.yml`) runs both on every push — don't publish a red commit. When adding a migration, add it to the `MIG` list in `run.sh`. New schema changes go in a new numbered migration; publish an app change only after its migration is run.
- Pages call database functions (`/rest/v1/rpc/<fn>`) with plain `fetch` (`api.js`). All tables have RLS on and no grants. Guests (anon) may only call `guest_menu`, `guest_state`, `guest_order`, `guest_call`, `guest_bill`, `guest_review`, and each needs the table's secret QR token. Prices are always worked out in the database (`price_cart`, `visit_bill`), never taken from the browser.
- **Demo mode**: when `supabaseUrl`/`supabaseKey` in `config.js` are empty (or `?demo` is in the URL), `demo.js` runs the same functions in the browser on a sample restaurant ("The Copper Pot"), saved in localStorage and shared between tabs. With no staff tab open, a pretend kitchen moves new orders along so a single phone demo works. **Any change to a database function must be mirrored in `demo.js`** (same inputs and output shape).
- Roles: owner (all) · manager (all but Settings; may pause ordering) · waiter (floor, kitchen, bills, take orders, mark paid, cancel New orders) · kitchen (kitchen screen, sold-out switches). Checked in SQL (`is_floor`, `is_manager`, `is_owner`) and mirrored in `staff.js` NAV.
- Logins: Supabase Auth email/password. First login = owner; later ones start switched off (one-restaurant install). Since 0004 role and on/off live in `memberships` (per restaurant), not `staff.role/active`. Team screen uses the edge function `supabase/functions/team-admin` (deploy via the Supabase editor).
- Dish photos: public Storage bucket `menu-photos` (managers upload; shrunk to 1000 px JPEG in the browser).
- Many restaurants (0004, DineOS): `restaurants` + `memberships`; every data table has `restaurant_id`. Staff functions work inside `my_restaurant()` (last picked via `staff_switch_restaurant`, else oldest active membership); guests are placed by the table token. Trigger `a_restaurant_id` fills restaurant_id from the parent row and refuses any cross-restaurant link; `price_cart(items, restaurant)` only prices that restaurant's dishes. Order numbers count per restaurant. New tables need `restaurant_id` + the trigger + a test in `test_0004.sql`. Invites join via `app_metadata.restaurant_id` (service key only, set by team-admin); team-admin changes a login's email/password/deletes it only when `owner_controls_login` is true. Photos go in `menu-photos/<restaurant_id>/…` (top folder allowed only while there is one restaurant).
- Safety rules (0003): every migration must start from the locked default (`alter default privileges … revoke execute`) and grant each new function explicitly; guests may run only the six `guest_*` functions (tested). Orders carry a `request_id` (idempotent); order status moves only by `order_step_ok()` steps and never on paid/void bills; every payment is a row in `payments` (method, amount, reference); activity log records payments, price/menu changes and split/tip changes via triggers.
- Money (since 0005): subtotal → minus discount (pct or amount, never more than the subtotal) = net → service % on net → GST % on (net + service) → total rounded to the rupee → tip % on net (rounded). Split = ceil(grand / ways). Frozen on the visit (incl. `discount`) when paid. `Money.bill(lines, s, tip, split, disc)` in api.js mirrors it.
- 0005 (POS, kitchen, close): discounts via `staff_set_discount` (manager up to `settings.max_discount_pct`, owner unlimited, logged); takeaway visits have `kind='takeaway'`, no table, `token_no` (per restaurant, restarts daily) via `staff_takeaway_order`; payments go through `pay_visit` (internal) from `staff_pay(parts)` or the old `staff_mark_paid` — one `payments` row per part, `paid_method='mixed'` when methods differ; takeaway can be paid before cooking and its orders keep moving (not cancelled) after payment; `settings.stations`, `categories.station`, `items.station` ('' = section's), copied to `order_items.station`; `staff_item_done` ticks a dish (all ticked → Ready); `day_closes` table + `staff_day_summary`/`staff_close_day` (manager) / `owner_reopen_day` (owner, logged) — a closed day refuses orders and payments; team notice in `settings.team_notice*` via `staff_set_notice`, shown in `staff_live.settings.notice`. Helpers `visit_label`, `day_closed`, `next_token`, `station_ok`, `insert_order_items`, `pay_visit`, `order_open` are granted to nobody (tested).

## DineOS app (`web/`, branch `dineos`)
- Next.js 15 + TypeScript + Tailwind 4, static export: `index.html` = staff app (hash routes `#/today #/pos?table=… #/floor #/kitchen #/design`), `t.html?k=<token>` = guest page (same address as the QR codes). Keys: `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_KEY` (publishable key only); empty = demo.
- Hosting: Cloudflare Workers **static assets only** (`web/wrangler.jsonc`, `web/public/_headers`), same as Studio CRM / tdw-crm. No Worker code, so the free plan's 10 ms per-request limit never applies; keep it that way (server logic goes in Supabase). Cloudflare setup: Workers & Pages → Import repository, root `web`, build `npm run build`, deploy `npx wrangler deploy`, build variables `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_KEY`.
- Data: `src/lib/api.ts` (fetch + session, same calls as `api.js`), `src/lib/staff.tsx` (staff_me, staff_restaurants, staff_live every 4 s, `useAction`), shapes in `src/lib/types.ts`. Screens in `src/screens/`. Demo mode loads the shared `demo.js` (copied to `public/legacy/` by `scripts/copy-demo.mjs` before dev/build), so **mirror DB changes in `demo.js` once and both apps get them**.
- Tests: `node tests/journey.mjs` (demo, `WIDTH=390` for phone) → `DINEOS JOURNEY PASSED`; `tests/real/run.sh` (needs Postgres + `POSTGREST=` v12 binary) runs the built app against the real migrations → `REAL STACK PASSED`. CI job `dineos` runs typecheck, lint, both.
- Screens (`src/lib/routes.ts` = the list and roles): Today, POS, Floor, Kitchen, Bills · Menu, Tables & QR (QR via qrcode-generator 1.4.4, print sheet `@media print` in globals.css), Team (role/on/name via `owner_edit_staff`; add/password/delete/email via team-admin), Settings · Help. Password-reset links (`#…type=recovery`) open Set a new password (`Auth.takeRecovery`).
- **Help guide rule (DineOS):** `src/content/guide.ts` — `GUIDE` is `Record<Route, Section>` so a screen without a Help section doesn't build; every visible change updates its section + a `WHATS_NEW` line in the same commit.
- Photos upload to `menu-photos/<restaurant_id>/…` (`uploadPhoto` in api.ts).
- Live: https://dineos.littlegasp-orders.workers.dev (Cloudflare account littlegasp.orders, project `dineos`, production branch `dineos`). Supabase: org DineOS, project `dineos` (ref amthbdgwonzgesxrphxc, Mumbai), migrations 0001–0004 + sample menu run 11 Nov 2026, sign-ups off.
- 0005 is written and tested on branch `dineos-0005` (not yet run on the live Supabase). Still not built: push alerts, offline order queue, receipts, guided tour, cashier role.

## Files
- `t.html` + `guest.js` + `guest.css` — guest page (`t.html?k=<token>`). Mobile-first, dark by default with a light version; accent colour from Settings.
- `staff.html` + `staff.js` + `staff.css` + `staff-guide.js` — staff app (hash routes `#dash #floor #kitchen #bills #menu #tables #settings/<tab> #help`). Studio-CRM-family layout (frosted panels, floating sidebar, bottom tab bar on phones, light/dark) in Dinedot colours. Polls `staff_live` every 4 s; sound + toast on new orders and calls.
- `index.html` — product page (photo hero, six steps with real app screenshots, kitchen/floor/owner sections, FAQ). Screenshots in `img/site/shot-*.jpg` are made by `tools/shots.js` (run with a local server on :8765, then convert PNG→JPG); retake them whenever a guest or staff screen changes.
- `img/menu/<dish-slug>.jpg` (800 px) and `img/cover.jpg` — demo restaurant photos (made in Canva, Nov 2026); `img/site/` — product page photos and screenshots. `config.js` — the only per-restaurant file. `vendor/qrcode.js` — qrcode-generator 1.4.4 (MIT).

## Rules
- **Help guide rule:** every visible staff-app change updates `staff-guide.js` (its section + a `WHATS_NEW` line) in the same commit.
- Keep parallel screens consistent (same drawer, list and button patterns).
- Testing standard: check guest and staff pages at 390 px and 1440 px, light and dark, and run the SQL tests.
- Guest privacy (DPDP): the system never asks guests for name, phone or email; no tracking scripts; keys only the publishable one in `config.js`.
- Payments: UPI deep links to the restaurant's own UPI ID (zero fee); staff confirm with Mark paid. A gateway (auto-paid) is a later phase.
